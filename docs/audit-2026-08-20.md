# CodeRelay implementation audit — 2026-08-20

Scope: every file under `src/` as of this date (~3.4k lines). Findings are ordered
by severity. Each one names the invariant it breaks, not just the symptom.

Status note: the competitive-landscape and provider-API sections of the research
brief are **not** in this document. They require live web access, which was
unavailable when this was written. Nothing below depends on an external source —
it is all derived from the code in this repository.

**Revision, same day:** every finding below has since been fixed. Each one keeps
its original text, because the reasoning is the useful part, and carries a
`Resolved` note naming what changed and where the behaviour is now pinned by a
test. The suite is 377 tests, all passing, with no network and no extension host.

## P1 — `maxTurns` counts attempts, and `stepId` changes on retry

`AgentLoop.turnLoop` increments `this.turn` on every iteration, and every routing
decision that continues the task (`RETRY_SAME`, `SWITCH_CREDENTIAL`,
`SWITCH_MODEL`, `COMPACT_CONTEXT`) returns `CONTINUE`, which re-enters the loop.
So a retry consumes a turn.

Two consequences:

1. `maxTurns` is documented as "Hard stop on model turns, so a looping model
   cannot run forever", but it actually bounds *attempts*. A task that burns the
   full `maxTotalAttempts: 8` retry budget has only 24 of its 32 turns left. The
   two budgets are supposed to be independent.
2. `ids()` claims: "`stepId` deliberately does *not* change between attempts of
   the same turn: the same tool call retried after a provider failure is the same
   effect, and must not look like a new one." This is false as written — `stepId`
   is `${taskId}#turn-${this.turn}`, and `turn` has already been incremented.
   Since `computeSideEffectKey` folds in `stepId`, the same tool call requested
   again after a transient failure produces a *different* `SideEffectKey`.

The practical blast radius today is small, because a truncated stream discards
incomplete tool calls, so a retried turn usually has no recorded
`TOOL_REQUESTED` to collide with. But the stated invariant is load-bearing for
future work (notably provider-level retry of a turn that *did* emit a complete
tool call), and it does not hold.

Fix: separate the two counters. Keep `turn` as the logical step, add an
`attemptsThisTurn`, and derive `stepId` from `turn` only — incrementing `turn`
only when a turn actually completes or a tool is dispatched.

**Resolved.** `attemptTurn` now returns a `TurnStep` carrying `sameTurn`, and
`turnLoop` advances `turn` only when `sameTurn` is false. `stepId` derives from
`turn` alone; `attemptsThisTurn` carries everything that varies per try, which
also makes `attemptId` unique across a task without a global counter. Pinned by
`test/agent/loop.test.ts`: a retry, a credential switch and a model switch all
keep one `stepId` while changing `attemptId`; `maxTurns: 1` still completes a
task whose first attempt failed.

## P1 — `planRecovery` discards the partial text of a truncated turn

The loop writes `MODEL_RESPONSE_COMPLETED` with `reason: 'truncated'` *before*
routing a truncated turn as a failure (`loop.ts`, the `outcome.ok` branch). That
is the right call for the timeline. But it breaks recovery on restart:

- `planRecovery` scans backwards and returns `START_TURN` on the first
  `MODEL_RESPONSE_COMPLETED` it sees, regardless of `reason`.
- `latestPartialText` likewise returns `null` as soon as it hits
  `MODEL_RESPONSE_COMPLETED`.

So if the process dies after a truncated turn is recorded, recovery starts a
fresh turn and throws away the partial output — the `REGENERATE_TURN` path with
`partialText` is unreachable in exactly the case it was written for.

`buildHandoff` gets this right (it treats `reason === 'truncated'` as
not-completed and routes the text into `truncatedText`). The two ledger readers
disagree about what a truncated completion means.

Fix: both functions must branch on `reason === 'truncated'`. In `planRecovery`,
a truncated `MODEL_RESPONSE_COMPLETED` should yield
`REGENERATE_TURN` with `entry.text`, not `START_TURN`.

**Resolved.** Both readers now branch on `reason === 'truncated'`, so the two
agree: a truncated completion is not a completed turn. `planRecovery` yields
`REGENERATE_TURN` with the partial text, and `partialFrom` stops its backward
scan only at a *cleanly* completed turn. `test/agent/loop.test.ts` resumes a
ledger whose last entry is a truncated completion and asserts the partial text
arrives in the next prompt as a `note`, labelled as a hint rather than as
something the model said.

## P1 — `CredentialManager` has a read-modify-write race

`patch()` does `this.records()` → map → `write()`, and `records()` reads the
whole array out of the Memento. Nothing serializes these. Two concurrent patches
to *different* credentials will clobber each other, because each writes back a
full array built from a stale read.

This is reachable on the normal path: `next()` patches `lastUsedAt` while
`reportFailure()` (from a previous attempt's `handleFailure`) patches
`coolingUntil`. Losing the `coolingUntil` write means a rate-limited key goes
straight back into rotation.

`ExecutionLedger` already solves this problem for itself with a promise chain
(`this.tail`). `CredentialManager` needs the same treatment.

**Resolved.** `CredentialManager` serializes its writes through the same
promise-chain pattern as `ExecutionLedger`, so a patch always reads state that
includes every earlier patch. `test/credentials/store.test.ts` fires concurrent
patches to different credentials and asserts neither write is lost.

## P1 — `authHeaders` puts provider logic outside `src/providers/`

`credentials/store.ts` ends with:

```ts
export function authHeaders(providerId: string, secret: string) {
  if (providerId === 'anthropic') {
    return { 'x-api-key': secret, 'anthropic-version': '2023-06-01' };
  }
  return { authorization: `Bearer ${secret}` };
}
```

This contradicts the rule stated in `core/types.ts` ("Nothing in this file may
reference a specific AI provider") and in `adapter.ts`. More importantly, the
`(providerId, secret) -> headers` shape cannot express several providers on the
target list:

| Provider | Auth shape | Fits current signature? |
|---|---|---|
| Anthropic | `x-api-key` + version header | yes (special-cased) |
| OpenAI / OpenAI-compatible | `Authorization: Bearer` | yes |
| Azure OpenAI | `api-key` header, plus `api-version` in the query string | **no** — needs URL control |
| Gemini | key as header or query parameter | **no** — needs URL control |
| AWS Bedrock | SigV4: signature over method + path + headers + **body hash** | **no** — needs the whole request |
| GitHub Copilot via `vscode.lm` | no HTTP request at all | **no** — not this transport |

Bedrock is the sharp case. SigV4 signs the body, but the loop merges auth headers
*after* `buildRequest` has produced the body, and `buildRequest` never sees the
secret. So request signing is currently unrepresentable, not merely unimplemented.

Fix: move auth onto the adapter as a method that receives the full unsigned
request and returns a signed one — `sign(request, secret) -> BuiltRequest`. That
covers all six rows above, keeps the secret inside the provider layer, and lets
the loop stay ignorant. Copilot needs a second adapter *kind* (see below).

**Resolved.** `authHeaders` is gone; `credentials/store.ts` now carries an
explicit note saying why nothing of the kind belongs there.
`ProviderAdapter.sign(request: BuiltRequest, secret: string): BuiltRequest` is
the single path from a secret into a request, and it receives the URL, headers
and body, so the four "needs URL control"/"needs the whole request" rows above
are now *expressible* — Azure, Gemini and Bedrock remain unimplemented, but no
longer unrepresentable. The structural objection is answered; the adapters are
still outstanding (see coverage below). `test/agent/loop.test.ts` asserts the
request carries exactly the builder's headers plus what `sign` added, that no
`authorization` header appears from anywhere else, and that each provider signed
with its own key and only its own key.

Copilot via `vscode.lm` still needs a second adapter kind. That is a gap, not a
defect: nothing currently claims to support it.

## P2 — the context-overflow regex misses the real error strings

`mentionsContextLimit` tests:

```
/context (length|window)|too many tokens|maximum context|max_tokens/i
```

The literal space after `context` means the underscore forms that providers
actually emit do not match — e.g. OpenAI's `context_length_exceeded` error code.
A 400 carrying that code therefore falls through to the generic 4xx branch and is
classified `CONFIG` (fail fast, "check model id and parameters") instead of
`CONTEXT` (compact, or move to a bigger window). That turns a recoverable
situation into a dead end.

Fix: `/context[ _-](length|window)/` and friends. This is one of the classifier
branches most worth a table-driven test per provider, once real error bodies can
be collected.

**Resolved.** The separator is now a character class, so the space, underscore
and hyphen forms all match. `test/recovery/classify.test.ts` covers
`context_length_exceeded` explicitly. The table-driven per-provider test is still
worth doing once real error bodies can be collected.

## P2 — `AUTH` conflates "key is invalid" with "key may not use this model"

`classifyFailure` maps both 401 and 403 to `AUTH` with `rotateCredential: true`,
and `CredentialManager.reportFailure` then sets `disabledReason` — permanently
sidelining the key until a human re-enables it.

401 justifies that. 403 frequently does not: it is also how providers say "this
key is not enabled for this model", "this region is not permitted", or "your org
blocked this endpoint". Disabling the key in those cases takes a credential that
works fine for every other model out of rotation entirely.

Fix: keep 401 → disable. Treat 403 as scoped to the `(credential, model)` pair —
prefer `SWITCH_MODEL` on the same credential over disabling the credential.

**Resolved.** `ErrorClass` gained `FORBIDDEN`, documented on the type as "the
credential is valid but not permitted for this model/endpoint/region". 401 still
maps to `AUTH` and disables the key; 403 maps to `FORBIDDEN`, which
`CredentialManager` does not disable on and which `route` sends through
`afterForbiddenPairing` — a model switch on the same credential. Covered in
`test/recovery/classify.test.ts`, `test/policy/route.test.ts` and
`test/credentials/store.test.ts`.

## P2 — `route()`'s `TOOL`/`FILESYSTEM` branch is unreachable, and wrong if reached

`route()` returns `GIVE_UP` for `errorClass: 'TOOL' | 'FILESYSTEM'`. But nothing
routes those: `dispatch()` handles tool failures itself by appending a `FAILED`
entry and pushing the message into the transcript so the model can react. That is
the right behaviour — a failing test is information, not a reason to abandon.

So the branch is dead code that, if ever wired up, would abandon tasks that
should continue. Either delete it, or make it explicit that these classes never
reach the router (an exhaustiveness `never` on a narrowed type would be better
than a live-looking branch).

**Resolved.** Taken the stronger of the two options: `RequestClassification`
narrows `errorClass` to exclude `TOOL` and `FILESYSTEM`, so the router cannot be
handed one, and the dead branch is gone rather than merely commented. Routing a
tool failure is now a compile error instead of a runtime surprise.
`test/agent/loop.test.ts` confirms the intended path — a failing tool and a
hallucinated tool name both come back as transcript context and the task
continues.

## P3 — smaller items

- **`RETRYABLE_STATUS` includes 409 and 425.** Neither is a normal transient for
  these APIs; 409 in particular is usually a genuine conflict that will recur.
  **Resolved:** the set is now `{408, 429, 500, 502, 503, 504, 529}`.
- **Attempt-budget check precedes classification.** `route()` returns `GIVE_UP` on
  `attempts.length >= maxTotalAttempts` before looking at `errorClass`, so a
  `TLS_UNTRUSTED` failure on the last attempt loses its actionable
  "trust your proxy's CA" escalation and degrades to a generic give-up.
  **Resolved:** `route` is now `withinAttemptBudget(input, limits, decide(...))`.
  The budget still stops anything that would continue automatically, but an
  `ESCALATE` passes through untouched — escalating already stops, and its
  question is the actionable thing the classifier learned — and a classified
  `GIVE_UP` keeps its own reason with the budget prefixed as context. Three tests
  in `test/policy/route.test.ts` pin those three cases.
- **One `fsync` per 500 characters of output.** `STREAM_PROGRESS` is appended from
  the streaming sink and `ExecutionLedger.append` syncs on every entry. Progress
  entries are the one class of entry that no side effect depends on — they exist
  only to feed `REGENERATE_TURN`. They could use a non-syncing append path
  without weakening the durability contract that matters.
  **Resolved:** `ExecutionLedger.appendEventual` writes without waiting for
  `fsync`, and its parameter type is `EventualEntryInput = Extract<…, { type:
  'STREAM_PROGRESS' }>` so the exemption cannot spread to an entry something is
  ordered against. Ordering is unchanged: it still goes through the same append
  chain, only the *waiting* is dropped.
- **`progress` array is unbounded** within a turn; harmless but grows with output
  length.
  **Resolved:** one promise is tracked instead of a list. Each progress entry
  carries the whole text so far and the ledger serializes appends, so awaiting
  the newest awaits every earlier one. The await also swallows rejections: a
  succeeded turn must not be reported as failed because a hint could not be
  written.
- **`nonce` is generated for a webview created with `enableScripts: false`.**
  Either add the CSP that uses it, or drop it.
  **Resolved:** the nonce is used, by the CSP's `style-src 'nonce-…'` for the
  inline stylesheet. `script-src` is omitted entirely under `default-src 'none'`,
  which is stricter than a script nonce would be and matches
  `enableScripts: false`. `test/ui/webview.test.ts` asserts both the nonced
  `style-src` and the absence of any `script-src`.

## Coverage against the research brief

What the code already answers, and answers well:

- **§7 partial-stream recovery.** The `SseParser`/`StreamDecoder` split, the
  refusal to dispatch an unterminated event, and the discarding of incomplete
  tool-call arguments are the correct primitives. `truncated` as a distinct
  `StopReason` from `length` is the right distinction.
- **§9 continuity ledger.** Append-only JSONL, `fsync` before the effect,
  torn-tail tolerance, `seq` gaps as a lost-write signal. The write-ahead
  ordering in `ToolRunner.run` is the real contribution.
- **§10 file safety.** `preState`/`expectedPostState` fingerprints make the
  ambiguous window resolvable by evidence rather than by guessing.
- **§11 git checkpoints.** Private `GIT_INDEX_FILE`, unreachable refs under
  `refs/coderelay/`, never touching `HEAD`/`refs/heads`, read-only `restore`.
  This is a careful design; the "no destructive commits" requirement is met.
- **§8 cross-model continuity.** `policy/handoff.ts` reconstructs rather than
  replays, and tags every claim `observed` vs `inferred`. The reasoning about why
  transcript replay is unsound (signed thinking blocks, provider-scoped tool ids)
  is correct and is the part most competitors get wrong.
- **§14 recovery policy.** `route()` is pure and capability-gated, and `degraded`
  surfaces silent downgrades instead of hiding them.
- **§12 the agent loop.** Now covered end to end with no network and no editor.
  The two invariants worth naming: a cancelled request is never routed, retried
  or recorded as a failure; and request outcome is not task outcome, so a
  truncated turn is recorded honestly and then routed as a failure rather than
  mistaken for a finished one.

What is missing entirely:

- Adapters for Gemini, NVIDIA, Azure, Bedrock, OpenRouter, local runtimes. The
  interface can now *express* all of them (`sign` receives the whole request), so
  this is implementation work rather than a design change.
- A second adapter kind for `vscode.lm` (Copilot), which is not HTTP+SSE. This
  one *is* a design change: `ProviderAdapter` assumes a request and a byte
  stream.
- Any wiring of `AgentLoop` into `extension.ts`. Today the extension can only
  *view* ledgers; there is no command that starts or resumes a task, no provider
  registration, no credential-entry UI. This is now the largest single gap: every
  component the MVP needs exists and is tested, but nothing in the editor can
  reach them.
- Health monitoring as a distinct concern (§13). It currently lives inside
  `CredentialManager` and tracks only `consecutiveFailures` / `coolingUntil` —
  no latency, no success rate, no per-model or per-endpoint state.
- Offline detection (§6, §20). Nothing distinguishes "no network" from "provider
  down", and there is no queue-and-resume-on-reconnect path.
- Context management beyond reusing the handoff as a compaction (§8). No token
  accounting, so `CONTEXT` failures are only ever detected reactively from a
  provider error.
- Benchmark harness (§23), failure injection suite (§24), cost tracking, MCP,
  prompt-injection defence (§19).

## One design proposal worth recording

`ToolSafety: 'unsafe'` currently forces `ASK_USER` for every interrupted shell
command, because there is no way to tell whether it ran. That is honest, but it
means any crash during a test run parks the task on a question.

There is a sound way to narrow it: have the terminal tool redirect its output to
`<storage>/effects/<sideEffectKey>.log` and create that file *before* executing.
Then the log's existence is evidence execution began, and a recorded exit code in
it is evidence it finished. That converts many `unsafe` cases into
`idempotent`-like ones with real evidence, without ever guessing. It does not
solve the general problem (a command with external side effects is still
unsafe to repeat), but it removes the most common false ambiguity.
