01Executive summary

The brief asked for research before implementation. The implementation already exists — and it is better than the market. What the research changes is narrower and more useful than a design: it kills four novelty claims, validates one, and surfaces one API capability the current design does not exploit.

What the research actually settles

  1. Multi-provider routing, multi-key rotation, cooldown, health-based routing and context-window fallback are commodity. LiteLLM ships all of it; OpenRouter ships two layers of it server-side; Kilo Code ships it inside a VS Code agent as “Virtual Quota Fallback”. Sections 4, 12, 13 and 14 of your brief describe a solved problem. Do not position on them.
  2. Git-based checkpointing is commodity and slightly discredited. Cline and Roo Code both ship shadow-git checkpoints. Their open issue trackers are full of nested-repo failures, large-repo timeouts and corruption reports. Your implementation avoids those specific failure modes by construction, which is a quality claim, not a novelty claim.
  3. Cross-provider continuity with side-effect safety is genuinely unoccupied. Every failover system found operates at the request layer: it retries a request somewhere else. None reasons about whether the interrupted request already changed the workspace. That gap is where the whole product lives.
  4. The thesis has independent academic support. AgentChaos (ASE 2026) injected 65 fault configurations into agent systems and found pass@1 dropping by up to 50 points, concluding that “robustness depends on system implementation rather than model capability.” That is your product statement, published, with numbers.
  5. One capability is being left on the table. OpenAI’s Responses API supports genuine stream resumption — background: true plus stream: true, reconnecting with starting_after=<sequence_number>. CodeRelay currently only regenerates truncated turns. Regeneration is the correct universal fallback; resumption is strictly better where offered, and the adapter interface cannot currently express it.

02Current competitive landscape

Grouped by what they actually are, because the brief’s list mixes three different categories of product that fail in different ways.

Category A — Agent harnesses (CLI)

Claude Code. Sessions persist as append-only JSONL under ~/.claude/projects/<project>/<session-id>.jsonl; --continue and --resume deserialise the full history back into context. Hooks fire around the tool lifecycle (PreToolUse, PostToolUse, UserPromptSubmit, SessionStart, Stop, plus PreCompact/PostCompact). Subagents get isolated context windows, their own tool permissions and their own model. fact Single-vendor by construction: there is no provider failover because there is no second provider. The transcript format is explicitly internal and may change between releases — inference do not build a parser against it.

OpenAI Codex CLI, Gemini CLI. Same shape, same single-vendor constraint.

Aider, Goose, OpenHands, SWE-agent. Multi-provider by configuration, not by failover. OpenHands users reach for external routing layers to get circuit-breaking; Goose’s documented “automatic fallback” is about secret storage falling back to file-based when the keyring is unavailable, not about models. fact

Category B — VS Code / IDE agents

Cline & Roo Code. The closest prior art on state. Cline maintains a shadow Git repository separate from your real history and commits after each tool use, capturing untracked files too. Roo Code forked from it. Both ship checkpoint restore. fact Both have well-documented reliability problems with it: checkpoints disabled by nested git repos, 15-second initialisation waits on large repositories, and at least one report of task history being destroyed while stuck on “Still initializing checkpoint…”. fact

Kilo Code. The single most important competitor for your brief. Its Virtual Quota Fallback provider is a synthetic profile wrapping an ordered list of real profiles; when profile 1 exhausts its manually-entered quota, it moves to profile 2, then 3. fact This is §4 and §14 of your brief, shipped, in a VS Code agent. The limits are that quotas are hand-entered rather than observed, and the switch is quota/rate-limit driven rather than error-classified — and, critically, it carries no reasoning about interrupted side effects.

Continue. Broad provider support; falls back to system-message tools for models without native tool calling, though that is opt-in rather than automatic. fact

GitHub Copilot. Now absorbs a large part of the multi-provider pitch: BYOK shipped for VS Code, letting Business/Enterprise users bring keys for Anthropic, Gemini, OpenAI, OpenRouter, Azure, Ollama and Foundry Local. fact Restrictions worth knowing: BYOK covers chat and utility tasks but not code completions, and is key-based auth only — no Entra ID or managed identities.

Cursor / Windsurf. Per-task model swapping across Claude/GPT/Gemini, agent checkpoints and reverts in both. Recovery in Cursor is better separated (inspect terminal, reject edits, restore checkpoint, or fall back to Git). Closed source, so nothing here is reusable, but they set the UX bar for §17’s timeline.

Category C — Gateways and routers

LiteLLM. The reference implementation of everything in §4/§12/§13/§14. Fallbacks at three levels (call, Router, proxy); typed fallback strategies for general failure, context-window errors and content-policy errors; cooldown after allowed_fails; background health-check loops that evict a deployment from the pool before a user request lands on it; multiple keys per deployment. fact

OpenRouter. Two distinct failover layers, and the distinction is worth stealing: provider-layer failover is automatic and on by default (allow_fallbacks: true) retrying another provider of the same model on 5xx or rate-limit, with failed requests unbilled; model-layer fallback via the models array is opt-in and additionally covers context-length validation errors and moderation refusals. fact

Portkey, Cloudflare AI Gateway, Flock. Same category. Flock advertises multi-key rotation, 429 failover and vendor fallback, explicitly compatible with Aider, Continue, Goose and OpenHands — inference which is the clearest evidence that the agent tools do not consider failover their job.

The structural gap

Category C knows about requests but not about workspaces. Category A and B know about workspaces but treat a provider failure as a dead end the user resolves by clicking retry. Nothing in the survey sits in both. That is the entire opening, and it is a real one.

Reading the table

The bottom third is where CodeRelay is alone, and the top third is where it is one of many. That is a healthy shape for a differentiated product and a dangerous one for marketing: the features that are easiest to describe are the ones everybody has.

Three gap cells matter. Offline detection and cost tracking are table-stakes that competitors ship and you do not. True stream resumption is the opposite — nobody ships it, and one provider now makes it possible (§14).

The blind cells on cross-provider handoff are the important nuance: LiteLLM, OpenRouter and Kilo do send the next request to a different model. They just send it without knowing what the previous attempt did to the disk. Calling that “failover” is accurate at the request layer and misleading at the task layer.

Where CodeRelay is already ahead

Claude Code resumes by deserialising the full transcript back into context. That is sound within one vendor and unsound across vendors, for the three reasons policy/handoff.ts already states in its header comment: partial assistant output is not an assistant message, reasoning is not portable, and tool-call ids are provider-scoped. The research confirms all three — see §6 on Gemini thoughtSignature.

More importantly, a transcript records what was said. It does not record whether a tool’s side effect landed. Claude Code’s resume path cannot distinguish “the edit was written” from “the edit was announced and then the process died”. Your TOOL_EXECUTING-before-effect write-ahead ordering can. inference That is the single sharpest technical claim in the project.

Do not replicate

Claude Code’s value is the harness, and the harness is tuned against one model family. Cloning its surface would produce a worse Claude Code. The defensible position is orthogonal: be the layer that keeps a task alive when any harness’s provider fails.

05OpenAI analysis

The finding that should change the design

Genuine stream resumption exists

Setting background: true together with stream: true on the Responses API streams events immediately while retaining the ability to reconnect. Every event carries a sequence_number. If the connection dies, you resume with GET /v1/responses/{id}?stream=true&starting_after=42 — picking up after the last event you actually received. Cancellation is idempotent: repeat calls just return the final Response object. fact

This is a materially better answer to §7 of the brief than regeneration, and CodeRelay cannot currently express it. Constraints found:

  • Time-boxed. Developers report This response can no longer be streamed because it is more than 5 minutes old; Zero-Data-Retention projects keep response data on disk for roughly 10 minutes to enable async polling. inference Treat the resume window as ~5 minutes, not guaranteed.
  • Model-scoped. Background mode is documented against current GPT-5.x models, not universally.
  • Not portable. You can resume OpenAI’s stream. You can never resume it on Anthropic. Resumption is a per-provider optimisation layered under an unchanged universal fallback.
  • Polling states are queued / in_progress until terminal.

Required interface change

// core/types.ts — add to ModelCapabilities
readonly resumableStream: boolean;

// providers/adapter.ts — new optional capability, mirroring CompletionDecoder
export interface StreamResumer {
  /** Re-attach to an in-flight generation after `afterSequence`. */
  resume(handle: StreamHandle, afterSequence: number): BuiltRequest;
  /** Provider-side cancel, so an abandoned background run is not billed. */
  cancel(handle: StreamHandle): BuiltRequest;
}
export interface StreamHandle {
  readonly providerRunId: string;   // OpenAI response id
  readonly lastSequence: number;    // last sequence_number observed
  readonly startedAt: number;       // for the ~5 min staleness check
}

The ledger needs one new entry type, STREAM_HANDLE, appended as soon as the response id is known. planRecovery then gains a branch above REGENERATE_TURN: if a handle exists, is fresh, and its adapter implements StreamResumer, resume; otherwise fall through to today’s behaviour unchanged. inference Estimated 1–2 days including tests.

Other OpenAI-specific facts that bite

  • Two APIs, not one. Responses and Chat Completions differ in shape. Your openai.ts targets Chat Completions, which is right for MVP because it is what every compatible endpoint speaks — but background mode is a Responses-API feature, so resumption needs a second request builder, not just a flag.
  • max_tokens vs max_completion_tokens. Your maxTokensField setting already handles this, and the description in package.json correctly notes that guessing wrong is a 400 on every attempt that failover cannot route around. This is a good example of the project’s general instinct being right.

09Existing recovery systems

Recovery — as opposed to fallback — is much thinner ground.

Agent-side

  • Cline / Roo shadow git. Commits workspace state to a separate repository after each tool use, including untracked files. This is genuine state recovery. Its documented weaknesses are operational: nested repos disable it, large repos time out (now bounded at a 15-second wait), and corruption has destroyed task history. fact
  • Cursor / Windsurf checkpoints. Restore points plus revert. Cursor separates inspect / reject / restore / fall-back-to-git more cleanly.
  • Claude Code --resume. Full transcript restoration within one vendor.

Durable-execution literature

The general problem is solved and named outside this domain: checkpoint before the step, attach a stable idempotency key to each logical operation, deduplicate on it, prefer upserts and conditional writes over blind writes, and check current state before acting. The canonical framing of the hard case matches CodeRelay’s exactly — the checkpoint lands after the step, so a worker that dies mid-step leaves the runtime unsure whether the side effect fired. fact

CodeRelay’s answer is to move the durable marker before the effect (TOOL_EXECUTING is fsync’d before the tool runs) and then resolve the resulting ambiguity from workspace evidence rather than from assumption. inference This is a correct application of a known pattern to a domain where nobody has applied it.

The honest novelty statement

“Durable execution with idempotency keys” is textbook distributed systems. “A coding agent that applies it to file edits and shell commands, and can therefore switch providers mid-task without re-running side effects” is, on this survey, unoccupied.

The two contracts that make it work

1. Decoding is separated from transport. A StreamDecoder turns SSE events into NormalizedEvents and never sees a socket, so every provider’s wire format — including its truncation behaviour — is testable with a string. This is why 381 tests run with no network and no extension host, and it is the reason the project can credibly claim reliability at all.

2. sign(request, secret) receives the whole request. A (providerId, secret) => headers signature cannot express Azure (api-version in the query string), Gemini (key as query parameter) or Bedrock (SigV4 over a body hash). Giving the signer the URL, headers and body makes all three expressible and keeps key material inside src/providers/.

Capability normalisation

The brief’s Provider → Credentials → Endpoint → Model → Capabilities tree is implemented, with one deliberate inversion worth defending: capabilities are declared by the user, not guessed by the extension. The reasoning in package.json is correct — a capability table shipped inside an extension goes stale and becomes “a confident lie about a context window”, and a wrong toolCalling guess either sends tool definitions to a model that cannot use them or silently hides a model from the router.

inference The cost is onboarding friction, and it is real. Mitigation for Phase 2: ship an optional, versioned, clearly-dated capability catalogue as a seed for the settings UI, which the user confirms and can override. Seeded-then-owned, never inferred at runtime.

  • 409 and 425 are deliberately not retryable. A conflict recurs on an identical retry; Too Early only arises from TLS early data this transport never sends.
  • The HTML-instead-of-JSON check only fires below 400. A 5xx carrying an HTML error page is the provider failing, not a captive portal, and saying “captive portal” there sends the user chasing the wrong problem.
  • Attempt budget wraps the decision rather than preceding it. withinAttemptBudget(input, limits, decide(...)) lets an ESCALATE pass through untouched on the last attempt, so a TLS_UNTRUSTED failure keeps its actionable message instead of degrading to a generic give-up.
Recommended addition

Add a CONTENT_POLICY class. Both OpenRouter and LiteLLM treat moderation refusals as a distinct fallback trigger, and they are right: a refusal is not transient, not a config error, and not a context problem — it is a signal to try a differently-aligned model. Today it would land in CONFIG or UNKNOWN and end the task.

The missing component

NetworkMonitor does not exist yet, and the prior audit names it correctly: nothing distinguishes “no network” from “provider down”. 14Streaming recovery architecture

The brief calls this critical. It is, and it is the part the codebase handles best.

The primitives already in place

  • An unterminated SSE event is never dispatched. Parsing is separated from decoding, so a half-arrived event cannot be acted on.
  • An incomplete tool call is discarded, not emitted. Both Anthropic and OpenAI stream tool arguments as JSON fragments; decoders buffer and emit only on the provider’s explicit end-of-call signal. finish() reports incomplete: true rather than guessing.
  • truncated is a distinct StopReason from length. length is a clean stop at the output cap; truncated means the transport died and we do not know what came next. Any unrecognised stop string — including null, content_filter, refusal, pause_turn — normalises to truncated, because guessing stop would tell recovery a turn finished when it did not.

Answering the brief’s eight questions

QuestionResolved by
Was the response complete?StopReason — truncated vs anything else.
Was a tool call issued?TOOL_REQUESTED in the ledger. Absent ⇒ no complete intent existed.
Was the tool executed?TOOL_EXECUTING is fsync’d before the effect runs, so its presence is exactly “may have run” and its absence rules it out.
Did the provider receive the request?Unknowable in general — and correctly treated as irrelevant. What matters is whether our workspace changed.
Could retry duplicate an effect?SideEffectKey = hash(tool + normalised args + stepId), with stepId stable across attempts of one turn.
Is the response resumable?Today: no. With §5’s change: yes on OpenAI, within ~5 minutes.
Continue from partial?Never as an assistant message. Carried in truncatedText, rendered under “Output that was cut off” with an explicit instruction not to assume anything it describes happened.

One correctness note on step 1

Resumption must be gated on the ledger, not only on handle freshness. If the interrupted stream had already emitted a complete tool_call that reached TOOL_EXECUTING, resuming the model stream and also resolving the tool from the ledger risks the model seeing its own tool call twice. Correct order: resolve tool state first (step 2), and resume only when step 2 finds nothing unresolved.

15Cross-model continuity architecture

The brief’s scenario — Claude edits five files, hits a rate limit, GPT continues, GPT fails, Gemini continues, and it feels like one task — is implemented in src/policy/handoff.ts. The design decision that makes it sound is stated in its own header: reconstruct, do not replay.

Why replay is unsound, with evidence

The packet

What the successor receives, all derived as a pure function of the ledger:

  • Objective — and if absent, that fact is reported, with an instruction to take no side-effecting action and ask.
  • Completed effects, each tagged observed (the tool reported its own result) or inferred (recovery concluded it landed from workspace evidence). The renderer states the difference in the sentence, not in a field the model might ignore.
  • Narrative from cleanly-completed turns only.
  • Truncated text in its own field so it can never be mistaken for a completed message, clamped to the tail — the tail is where the model stopped, and therefore the only part that says where to pick up.
  • Pending effects, split by mayHaveRun. False ⇒ “still needs doing”. True ⇒ “do not run it again; verify current state first”.
  • Prior models and compaction count.
The line that justifies the whole project

From the module header: “A successor model being told ‘the file was written’ when we only inferred it is how a recovery feature causes the corruption it exists to prevent.” No competitor surveyed makes this distinction, because no competitor has a state model capable of expressing it.

Gap: the ledger is not yet the compaction strategy

The prior audit notes that context management beyond “reuse the handoff as a compaction” does not exist, and there is no token accounting — so CONTEXT failures are only detected reactively from a provider error. LiteLLM’s enable_pre_call_checks is the proven pattern. inference Add an estimator and check the assembled request against the declared contextWindow before sending. Roughly 2 days, and it converts a class of task-ending failures into a routine compaction.

17Model routing and health

route() is a pure function — failure plus history plus candidates in, decision out — which is why 924 lines of tests can cover it without a network. Its principle is never repeat an attempt already known to fail: a rejected credential is never re-offered in the task even if the store has not caught up, a non-retryable failure never becomes a same-model retry, and a model past its per-model budget stops being a candidate.

The brief wants frontend→visual model, architecture→reasoning model, rename→cheap model. Currently health lives inside CredentialManager and tracks two fields. Feed it to route() as a tie-break among otherwise-equal candidates. inference ~2 days, and it is what turns “fallback” into “routing”. Persist to workspace state, never to telemetry.

21Benchmark system

Two 2026 papers define the ground here, and aligning with them is worth more than inventing a private methodology.

  • AgentChaos (arXiv 2608.06790, ASE 2026) — programmatic fault injection at the HTTP interface where agents reach LLMs, so it is non-intrusive and needs no source changes. One housekeeping note

policy/route.ts and providers/catalog.ts embed literal NUL characters as composite map-key delimiters. 33Final recommendation

Positioning

Of the two candidates, “Models can fail. Your task shouldn’t.” is stronger — and it is already the description in package.json. It names a failure the user has personally experienced, states the promise in four words, and implies the mechanism without overclaiming. “Your coding task doesn’t belong to one model” is a statement about architecture; users do not have architecture problems, they have interrupted-work problems.

“Reliable AI coding infrastructure for VS Code” works as the subtitle. Lead with the failure, follow with the category.

The seven decisions

  1. Stop researching. The research is done and it says the design is sound. The binding constraint is that extension.ts cannot start a task.
  2. Retire the commodity claims. Multi-provider, multi-key, cooldown, health routing, context fallback. LiteLLM, OpenRouter and Kilo have them. Leading with them invites the comparison you lose.
  3. Lead with side-effect safety. It is the one thing nobody else has, and every high-novelty item depends on the same ledger.
  4. Build the benchmark early, not last. It is your proof, your demo and your risk-check on the central thesis, all at once. Move it out of Phase 4 and run a crude version during Phase 1.
  5. Add the three small gaps — NetworkMonitor, pre-call context check, CONTENT_POLICY. Roughly four days for a real reduction in task-ending failures.
  6. Add stream resumption after the MVP ships. Genuinely better where offered, but it is one provider, a five-minute window, and an ordering constraint. Regeneration already works everywhere.
  7. Cut MCP and subagents from v1. They consume the schedule and, for MCP, import the threat surface that undermines the positioning.
Verdict

This is a strong project that is closer to done than the brief assumes. The architecture makes a real technical argument, holds up against everything found in this survey, and is validated in its central claim by two 2026 papers. The risk is not that it is unbuildable or unoriginal — it is that it stays a very good library that no one can run. Wire the extension, record the demo, publish the chart.
